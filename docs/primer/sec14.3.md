# 将自己的作品写入开发Wiki

当一个作品完成后，我们除了向玩家发布它，还可以将制作过程中解决的问题整理为教程，供其他开发者学习。在本节中，我们以向社区维护的**Bedrock Wiki**贡献文章为例，学习如何把“我做出了一个功能”转化为“别人也能理解并复现这个功能”。如果选择其他开发Wiki，也应先阅读目标站点自己的贡献约定。

## 从完整作品中选择一个问题

作品发布页关心玩家能获得什么，而技术文章关心一个问题如何被解决。假设我们制作了一张研究所地图，其中包含数十种模型、菜单和任务，直接把全部工程贴到Wiki上，读者很难判断应该先看哪里。

我们可以选择其中一个范围明确的问题，例如“怎样用纹理集比较金属度与粗糙度”。它既有具体目标，也能通过两个小文件复现，并且可以清楚说明适用的图形模式。这比“介绍我的大型研究所作品”更适合作为教程主题。

确定主题之后，先搜索Wiki中是否已有同类文章。若已有基础介绍，我们可以补充其中缺少的步骤、修正过时字段，或增加一个经过验证的例子。能够改善现有页面时，不必重复创建第二份几乎相同的教程。

## 整理最小可复现示例

**最小可复现示例**（**Minimal Reproducible Example**）应当只保留解释问题所需的内容。对于纹理集实验，通常无需包含任务系统、几十个无关实体或整张世界；一份资源包清单和一个纹理集就足以说明基本关系。

我们先把这个示例复制到独立目录，再从干净环境导入。这样可以发现对开发目录或其他包的隐含依赖。每个代码片段都应说明完整路径，并明确它是完整文件还是需要插入已有文件的局部内容。省略号不能藏在一个被标作完整JSON的代码块中。

如果示例依赖图片，也应提供自己有权分发的图片或可重建的制作步骤。截图展示结果，源文件帮助复现，两者的作用不同。只放一张成功截图，不能让读者知道包怎样组织。

## 写清楚因果关系

文章开头先说明目标、所需基础知识和适用版本。接着从读者已经理解的概念引入新概念，再给出步骤与结果。代码之后解释决定行为的关键字段，不必逐字翻译每一个花括号。

例如，对于本章的PBR实验，我们可以这样说明：

> 这里将基础颜色固定为浅灰色，是为了避免花纹干扰我们对反射的观察。首先保持金属度不变，只修改粗糙度；随后保持粗糙度不变，再比较金属与非金属表面。每次只改变一个变量，便可以判断画面中的差异来自哪一项设置。

这段文字解释了为什么这样设计实验，而不仅仅是“复制下面的文件”。随后还应补充没有变化时的排查顺序，以及经典模式与Vibrant Visuals的能力差异。完整教程需要帮助读者理解失败，而不只是展示作者成功的那一次。

## 标明证据的范围

我们可以用一张简短表格整理验证记录：

| 项目 | 应填写的实际内容 |
| --- | --- |
| 游戏 | 完整版本与正式版、预览版通道 |
| 平台 | 测试设备和系统 |
| 环境 | 图形模式、必要实验开关与依赖包 |
| 过程 | 从导入到产生结果的操作步骤 |
| 结果 | 已观察到的行为与仍未覆盖的情况 |
| 资料 | 官方文档地址及样本的固定提交链接 |

阅读源码、通过JSON校验和在游戏中运行，是三种不同的证据。若我们只完成前两种，就应这样表述；不能写成“已在全平台测试”。内部导出数据也应附上来源构建，并区分注册结构与普通附加包公开能力。

本文所引用的样本可以使用提交SHA固定地址，避免`main`更新后读者看到与正文不同的字段。描述预览版功能时，应明确当前通道，并说明正式版读者可以采用什么替代路径。

## 适应目标Wiki的页面结构

Bedrock Wiki的贡献说明采用GitHub拉取请求流程。正式动笔前，我们应查看它当前的页面编辑指南及附近页面，确认目录、前置信息、语言、代码组件和分类方式。

我们读取的页面编辑指南要求使用前置信息提供标题和描述，并说明标题由主题自动显示。因此，向该Wiki投稿时，不应再在正文顶部重复一个相同的一级标题。这个约定与本教程仓库的页面结构不同，迁移文章时需要相应调整。

署名、许可和示例文件的归属也应按照目标项目的要求处理。我们的原作品可以保留自己的名称，但通用教学例子应减少不必要的品牌或宣传内容。若需要将中文文章投稿到以英文为主的区域，还应按维护者接受的语言范围翻译与校对，而不是假定任何语言都能直接并入。

## 提交一份容易审阅的变更

在自己的分支中创建或修改页面，完成本地预览并执行目标项目要求的构建。重点检查代码块、图片路径、内部链接和前置信息，而不只是正文错别字。

然后提交范围明确的拉取请求，说明文章解决的问题、采用的资料版本、实际验证方法和已知限制。对于PBR实验，可以说明新增了可复现的常量纹理集示例，并记录设备与图形模式的测试范围。不要在同一个请求中顺便重排大量无关页面，使维护者难以看出本次真正的改动。

收到审阅意见后，沿同一主题修改并回复处理情况。页面合并只是维护工作的开始；游戏升级后若接口变化，我们还应同步更新步骤、示例和版本说明。这样，作品中的一次经验才能成为其他开发者长期可以依赖的资料。
