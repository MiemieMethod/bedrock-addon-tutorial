# 修改HAL

如果我们阅读较早的基岩版光影教程，便可能遇到“修改HAL着色器”这一说法。那些教程常常直接展示着色器源码的修改，而在当前客户端中重复相同步骤却未必产生任何效果。在本节中，我们将先说明这个标题的历史背景，再建立一套判断旧光影资料是否适用的方法。

## 先确认我们讨论的对象

**硬件抽象层**（**Hardware Abstraction Layer**，**HAL**）本来是计算机系统中的一般概念，用于隔离上层逻辑与具体硬件或底层接口的差异。在基岩版社区的旧资料中，“HAL”也常被用于指代RenderDragon普及之前的渲染实现及其光影开发方式。它并不是一种名为HAL的独立着色语言。

因此，当一篇旧教程说“修改HAL”时，我们还需要追问：它面向哪个游戏版本、哪个操作系统，以及哪种图形接口？使用GLSL语法的文件与使用HLSL语法的文件，不会因为同属于一个光影包就可以任意互换。文件名相似，也不能证明目标客户端会继续加载它们。

官方1.18.30更新说明记录了RenderDragon向Android、iOS、Switch及Windows 10 UWP x86版本的扩展。这个历史节点可以帮助我们理解大量旧教程的失效原因，但不能据此把所有更早平台简单归为完全相同的实现。

## 如何阅读一份旧光影包

我们先在独立目录中保留原始文件，记录作者说明、适用版本和许可证，再观察文件的职责。一般可以从以下几个问题逐步展开：

1. 哪一项资源声明选择了这个着色器？如果找不到引用，文件可能并没有参与当前场景的渲染。
2. 源文件的输入有哪些？哪些来自纹理，哪些来自顶点，哪些由游戏逐帧提供？
3. 文件最终输出什么？是位置、颜色，还是另一个阶段继续使用的数据？
4. 是否存在针对不同平台的条件编译？某个平台有效的分支，在另一个平台上可能根本不会编译。

这样的阅读顺序与我们阅读实体文件十分相似：先找到入口，再沿引用追踪数据，最后分析具体计算。直接搜索“亮度”并修改所有常数，通常无法得到可维护的结果。

例如，下面的GLSL风格片段展示了一种简单的颜色偏移思想：

```glsl
// 教学片段：baseColor由外部提供，并不是完整的游戏着色器。
vec3 tint = vec3(1.0, 0.85, 0.70);
vec3 tintedColor = baseColor.rgb * tint;
```

它保留红色分量，同时减弱绿色与蓝色分量，因而可能产生偏暖的观感。但是，它没有声明输入、输出、入口、纹理采样或引擎接口，也没有处理色彩空间。我们不能将它保存成某个猜测出来的文件名，然后把“没有变化”解释为参数不够大。

## 历史环境中的最小修改实验

如果我们已经合法拥有对应版本的测试环境和一份明确适配该环境的光影包，可以按照以下顺序进行研究：先在原始版本中确认未修改包的效果，再复制一个工作版本，只修改最终颜色中的一个无关游戏逻辑的系数。重新加载后，在固定场景中比较差异，并查看编译或内容错误。

实验结果至少有三种情况。第一种是画面出现预期色偏，说明修改所在的路径确实被使用。第二种是画面保持原样，说明还需要检查缓存、资源优先级或平台分支。第三种是整个表面异常、缺失或回退，说明编译、接口或资源配置可能出现错误。第三种情况不能当作“成功加载了新效果”。

我们应当把环境名称和版本一起保存在实验说明中。没有对应历史客户端时，能完成的是源码分析和接口对照，而不是运行复现。本教程没有提供历史客户端，也没有将上述教学片段标记为可直接安装的光影包。

## 将旧效果迁移到当前资源包

对于当前客户端，我们更实用的工作是把视觉目标拆解，再寻找公开的数据接口：

| 旧效果的目标 | 当前可以优先考察的方向 |
| --- | --- |
| 改变表面花纹或基础色 | 常规纹理或纹理集的颜色层 |
| 表现金属与粗糙表面的区别 | PBR纹理集的金属度和粗糙度 |
| 改变场景雾的视觉表现 | 目标版本支持的雾定义 |
| 调整Vibrant Visuals的环境表现 | 官方公开的光照、大气、水体及颜色分级接口 |
| 任意改变顶点位置或替换底层渲染阶段 | 先核实是否存在公开入口，不能由旧源码推定可用 |

我们不必把旧文件逐行翻译为新文件。比如，旧着色器通过复杂计算制造某种粗糙感，而当前PBR流程已经接收粗糙度数据，那么重新制作对应的数据层通常更符合当前接口的职责。

完成迁移之后，还需要在不支持该高级图形模式的设备上检查基础外观。这样，我们才能清楚说明作品的最低能力与增强效果，而不会把作者开发机上的表现误写成所有玩家都能看到的结果。
