# 加密并发布至服务器

有些作品并不以单独下载的形式提供，而是随着玩家加入服务器一同使用。此时，我们经常同时关心两个问题：怎样让服务器正确加载并分发资源，以及怎样保护自己的作品。在本节中，我们先完成可以复现的BDS部署流程，再说明内容加密真正涉及的边界。

## 服务器加载与客户端显示

**基岩版专用服务器**（**Bedrock Dedicated Server**，**BDS**）负责运行世界及其服务端逻辑，客户端则需要获得显示内容所需的资源。把文件复制到服务器并不等于世界已经启用它；世界的包列表、包清单和实际文件必须对应。

我们先准备一个已经在本地验证过的世界副本，其中包含实际启用的资源包和行为包。正常停止测试服务器，将世界目录复制到BDS的`worlds`目录下，不妨命名为`addon_lab`，再使`server.properties`中的名称与目录一致：

```properties
level-name=addon_lab
texturepack-required=true
content-log-file-enabled=true
```

这里的`texturepack-required=true`用于要求客户端使用世界需要的资源包。它是资源使用策略，不是内容加密开关，也不会把普通文件转换为加密包。

## 将包放在正确的位置

BDS既支持世界自身目录中的包，也有服务器根目录下供世界使用的`behavior_packs`和`resource_packs`。第一次实验可以保留从客户端导出的世界内包结构，减少额外移动造成的引用错误。

然后检查世界根目录的`world_behavior_packs.json`与`world_resource_packs.json`。其中的`pack_id`引用对应包清单的`header.uuid`，版本则对应包头版本。下面仅展示结构，其中的UUID代表教程中的独立示例身份：

```json
[
  {
    "pack_id": "6996c799-2e6e-440e-820e-ecbf1208cc9c",
    "version": [1, 0, 0]
  }
]
```

若使用的是我们自己的资源包，就必须替换成自己的真实包头UUID，不能照抄一个没有包含在服务器中的包。也不要把行为包记录填进资源包列表，或把模块UUID误当作包头UUID。

启动服务器后，先观察控制台和内容日志，确认世界被正确选中，依赖已经满足，脚本没有加载错误。随后使用协议版本相容的客户端进入测试服，观察资源下载过程及实际外观。预览版服务器应配合相容的预览版客户端，不能单凭版本名称相近就认定可以连接。

## 用更新实验验证分发

我们可以先在资源包中准备一个明显但无害的外观变化，例如第10章PBR实验中的石头颜色。首次进入时确认客户端得到该效果，再增加包版本、更新世界包列表，并在停止服务器后替换包文件。

重新进入时，检查客户端是否获得新版本。如果旧资源仍然出现，先对照包UUID、版本和服务器实际目录，再考虑缓存问题。不要一开始就让所有玩家删除全部资源；这既不利于定位，也可能删除与本服务器无关的内容。

发布前还应测试拒绝下载时的行为、资源下载失败时的提示，以及至少两名玩家同时加入的情况。如果资源决定关键玩法信息，就应说明为什么需要强制使用，而不是让未加载资源的玩家看到不可理解的模型或提示。

## 内容加密究竟保护什么

**内容加密**与ZIP压缩、代码混淆、连接过程中的传输保护都不是同一件事。为ZIP设置密码只会得到一个需要密码的压缩文件；Minecraft并没有因此自动获得读取它的流程。删除换行或重命名变量也只是提高阅读难度，并没有把明文变为需要密钥才能还原的内容。

真正的加密分发还需要约定文件如何加密、元数据如何记录、客户端怎样获得对应内容密钥，以及服务器如何声明这些资源。缺少任一环节，都可能得到服务器可以存放、客户端却无法加载的文件。

官方公开的BDS部署文档没有提供一个可在任意包上执行、并自动完成上述流程的通用加密命令。因此，本节不会虚构`encrypt-pack`之类的工具参数，也不会把Marketplace内部流程当作普通BDS附带功能。若使用具有明确文档的第三方服务器扩展，应另外记录其名称、版本、目标BDS版本和加密格式，并在隔离测试服验证完整的分发与更新流程。

## 保护作品时可以确定完成的工作

我们首先保留源码、原始素材、许可证和版本记录；仅分发运行需要的资源，避免误放账号信息、开发凭据或后台配置。必须由服务器控制的规则，就在服务端验证，不把客户端显示逻辑当作可信的权限判断。

即使资源经过加密，客户端为了显示模型与纹理仍需要在某个阶段使用其内容，因此不能承诺“任何人都无法获取”。加密可以服务于既定分发体系，却不能替代服务端权限检查、清晰许可和可靠更新机制。

更新时保留上一版世界和包的完整备份。若发生故障，停止服务器后恢复同一时点的世界、包和配置，再启动核查，避免只回退一份文件造成版本互相不匹配。
