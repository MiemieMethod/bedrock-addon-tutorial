# 修改原版纹理

从这一章开始，我们使用已经准备好的`Tutorial_RP`修改原版资源。先从最直观的变化开始：让泥土方块显示成一张由我们绘制的纹理。

## 找到被游戏使用的图片

**纹理**（**Texture**）是绘制在模型表面或界面中的图片。在[Mojang发布的原版样例](https://github.com/Mojang/bedrock-samples/tree/main/resource_pack)中，我们可以找到`textures/blocks/dirt.png`，这便是本节需要替换的泥土纹理。

这里要记住的是相对于资源包根目录的完整路径。`textures/blocks/dirt.png`和`textures/dirt.png`不是同一个位置；`Dirt.png`和`dirt.png`也不应当混用大小写。制作资源包时，应当统一使用与目标资源完全一致的路径和文件名，不能依赖某一台电脑的文件系统恰好不区分大小写。

原版样例仓库的`main`与`preview`服务于不同的版本范围。我们应先检查仓库中的版本信息，再选择与测试客户端对应的资料，不能从预览分支复制一个新资源名称，就认定较早的正式版已经提供这个资源。

## 绘制一张用于验证的纹理

在资源包中新建`textures`目录，再建立`blocks`子目录。使用图片编辑器新建一张16×16像素的图片，将它画成两种容易分辨的颜色交替出现的方格，保存为PNG，文件名为`dirt.png`。现在它的完整相对路径应为`Tutorial_RP/textures/blocks/dirt.png`。

选择方格图案，是为了让第一次测试的结果足够明显。待我们确认路径和加载过程正确之后，再把它替换为真正设计的泥土外观。不要同时修改路径、图案和资源包UUID，否则一旦失败，很难判断究竟是哪一处变化导致了问题。

如果希望直接使用仓库附带的技术测试图片，可以复制`examples/foundations/Tutorial_RP/textures/blocks/dirt.png`。这是一张程序生成的方格图案，不包含原版游戏资产。此时资源包里只需要已经完成的`manifest.json`和这张图片。

## 为什么不需要额外的方块定义？

我们可能会注意到，本节并没有编写一个名为`dirt.json`的文件，也没有修改纹理图集。这是因为原版泥土已经具有自己的定义，它仍然会寻找原来的纹理路径。我们在优先级更高的资源包中提供了相同路径的图片，游戏便可以用这张图片替代原来的资源。

如果我们把图片改名为`tutorial_dirt.png`，情况就不同了：虽然图片依旧存在于资源包中，原版泥土却不会因此自动改为寻找这个新名字。届时需要有相应的定义或引用，将这个新路径联系起来。我们将在自定义方块章节中进一步学习这种做法。

由此可见，**替换已有资源**与**增加一个新资源并引用它**是两个不同的过程。本节采用前者，所以相同路径本身就是建立联系的关键。

## 进入游戏观察

将资源包放入当前客户端的开发资源包目录，在测试世界中激活它，然后重新进入世界。我们同时观察世界中放置的泥土和物品栏中的泥土，确认预期使用该纹理的外观是否变化。若要便于检查，可以先在平坦场地放置几块泥土，分别观察其顶部和侧面。

接下来切换为生存模式，尝试挖掘泥土。即使它已经显示成鲜艳的方格，挖掘规则和掉落仍然属于泥土。将纹理换为石头的外观，也不会自动让铲子失效或让掉落物变成圆石。

我们还可以临时停用资源包后再次进入世界。泥土应当恢复原有外观，世界中已放置的方块不会因为资源包被停用而全部消失。这说明我们改变了客户端读取的图片，并没有把每一个泥土方块转换成新的方块类型。

## 查找没有变化的原因

如果纹理没有变化，先在游戏设置中确认资源包已激活，再检查是否有更高优先级的包提供了同一路径。随后检查文件名、实际图片格式和完整目录层级。仅将JPEG文件的扩展名改为`.png`不会完成图片格式转换，应使用编辑器的导出功能。

如果纹理出现拉伸、透明缺口或不合预期的边缘，则检查图片的尺寸和透明通道。对于本节的泥土测试，先使用完全不透明的16×16图片最容易排除干扰。图片编辑器中的缩放显示不会改变文件实际像素尺寸，导出时也不要无意间增加画布边距。

已经确认文件正确但画面仍显示旧版本时，保存文件并完整重启客户端，再检查是否修改了另一份同名包。比起不断重新生成UUID，这样能够更直接地定位资源缓存或副本混淆的问题。

本节完成后，大家可以尝试在同一资源包中再替换一种原版纹理。先从对应版本的样例确认路径，只增加这一张图片，再观察它影响了哪些游戏内容。同一图片可能被多个地方复用，因此“我只换了一张图片”并不总是意味着“只有一个物体会改变”。
