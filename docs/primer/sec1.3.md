# 从配方开始

有了清单文件，游戏已经有足够的信息识别我们的行为包，不过包中还没有任何可以改变游戏体验的内容。在本节中，我们为它添加第一个功能：将八块圆石围成一个方框，制作出四块石头。

这个配方只用于演示开发流程。它绕过了原版烧炼石头的过程，因此会改变生存玩法的资源成本。我们先把“功能是否按定义运行”验证清楚，再根据作品的实际玩法决定是否保留这种设计。

## 创建配方文件

在`Tutorial_BP`中新建`recipes`文件夹，再在其中新建`stone_from_cobblestone.json`。文件的完整相对路径为`Tutorial_BP/recipes/stone_from_cobblestone.json`。写入下面的内容：

```json
{
    "format_version": "1.20.10",
    "minecraft:recipe_shaped": {
        "description": {
            "identifier": "tutorial:stone_from_cobblestone"
        },
        "tags": ["crafting_table"],
        "pattern": [
            "CCC",
            "C C",
            "CCC"
        ],
        "key": {
            "C": {
                "item": "minecraft:cobblestone"
            }
        },
        "unlock": [
            {
                "item": "minecraft:cobblestone"
            }
        ],
        "result": {
            "item": "minecraft:stone",
            "count": 4
        }
    }
}
```

大家可以看到，整个文件仍然是一个JSON对象。`minecraft:recipe_shaped`描述的是**有序配方**（**Shaped Recipe**），即原料必须按照一定形状排列的合成配方。清单中的`format_version`为数值`2`，这里却是字符串`"1.20.10"`，正是因为两种文件各自使用自己的格式版本。

## 将合成格写成字符串

`pattern`是**图案**（**Pattern**），数组中的一个字符串对应合成界面中的一行，字符串中的一个字符对应这一行的一格。我们把三行依次展开，便可以得到下面的对应关系：

| 第一列 | 第二列 | 第三列 |
| --- | --- | --- |
| `C` | `C` | `C` |
| `C` | 空格 | `C` |
| `C` | `C` | `C` |

那么，`C`究竟表示什么呢？它并不是游戏预先规定的圆石缩写，而是我们自己选定的符号。真正将符号与物品联系起来的是`key`：本例把`C`对应到`minecraft:cobblestone`，因此八个`C`就是八个放有圆石的格子。中间的普通半角空格表示该格应当留空，不要把它换成全角空格，也不要为它再添加一份物品定义。

我们完全可以把所有`C`改成`A`，同时将`key`里的`C`改成`A`，得到的配方仍然相同。由此可见，字母本身的含义并不重要，**图案与映射中的符号保持一致**才重要。

`tags`中的`crafting_table`指定配方用于合成系统。本例需要三行三列，所以必须使用工作台，玩家物品栏中的二乘二合成格放不下这个图案。`result`描述合成结果，其中`item`是石头的物品标识符，`count`是一次完整合成得到的数量。

## 配方也有自己的身份

`description.identifier`是这个配方的**标识符**（**Identifier**）。我们使用`命名空间:名称`的形式，将它写为`tutorial:stone_from_cobblestone`。冒号前的**命名空间**（**Namespace**）用于区分不同来源的内容，冒号后描述具体对象。

`minecraft:`属于原版内容，所以引用原版圆石和石头时使用它；新增配方则使用我们的`tutorial:`。这里标识的是“合成规则”，不是石头这个物品。即使两种配方都产出石头，也应该为它们分别使用不同的配方标识符。给新的配方文件换一个文件名，却继续使用同一个标识符，不能得到两个相互独立的配方。

实际发布作品时，建议将`tutorial`换成与自己或作品有关的命名空间，并在全部引用中保持一致。本教程继续使用它，是为了让跨章节的示例容易对应。

## 配方解锁与实际合成

`unlock`中的条件让玩家在获得圆石之后解锁这个配方。这里使用数组，数组中的对象描述解锁条件。配方是否出现在配方书中，与手动排列原料是否能够合成，需要分别检查；世界的配方解锁规则和界面筛选状态也会影响观察结果。

下一节加载行为包后，我们可以在测试世界中准备一个工作台和至少八块圆石。获得圆石之后打开工作台，在外圈放置圆石、中间留空。按照本定义，结果格应当显示四块石头；取走结果时，八个原料格各消耗一块圆石。

随后再做两次对照：把中间一格也填上圆石，以及只在二乘二合成格里放圆石。两次都不应触发本例的配方。这样的对照可以帮助我们确认，游戏确实在按照图案判断原料，而不是简单地数一数物品栏里有没有八块圆石。

如果行为包能够加载，却没有合成结果，按顺序检查`recipes`目录的拼写、文件的JSON语法、图案中三个字符串的长度、`key`里是否定义了每个非空格符号，以及物品标识符是否写错。不要将`minecraft:stone`写成物品在中文界面上的名称，也不要给这个新配方添加旧教程中的物品`data`值；本例直接使用完整的物品标识符。

完成本节后，行为包只需要清单和这一份配方即可。我们在[下一节](./sec1.4.md)将它放入游戏，完成从编辑文件到验证效果的完整过程。
