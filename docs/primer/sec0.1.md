# JSON的语法

<a rel="license" href="http://creativecommons.org/licenses/by-nc-sa/4.0/"><img alt="Creative Commons License" style="border-width:0" src="https://mirrors.creativecommons.org/presskit/buttons/80x15/svg/by-nc-sa.svg" /></a>

JSON是一种用于记录和交换数据的文本格式，也是我们编写Minecraft附加包时经常接触的格式。包的名称、物品的属性、合成配方的原料，都可以按照相应规则写入JSON文件，再交给游戏读取。掌握这些规则，能够帮助我们分清“文件没有写对”和“功能没有配置对”，减少开发过程中反复试错的时间。

**JSON**全称为**JavaScript Object Notation**，译为**JavaScript对象表示法**。它的写法源于JavaScript，但已经成为独立于具体编程语言的数据交换格式。因此，即使我们还没有学习JavaScript，也可以先学会阅读和编写JSON。本章便从一个完整的清单文件开始，逐步认识其中每一种结构。如果大家已经熟悉标准JSON，可以直接阅读[第一章](./sec1.1.md)。

## 先观察一个清单文件

下面是我们将在第一章中使用的行为包清单。先不要着急记忆UUID、模块和版本的作用，我们只观察这些数据是怎样组织起来的：

```json
{
    "format_version": 2,
    "header": {
        "name": "教程行为包",
        "description": "从一个新的合成配方开始。",
        "uuid": "88d1db72-bbea-4f17-9671-409c60c40972",
        "version": [1, 0, 0],
        "min_engine_version": [1, 21, 0]
    },
    "modules": [
        {
            "type": "data",
            "uuid": "21a0b5ca-a7c7-4860-86a9-09bfa64e3c15",
            "version": [1, 0, 0]
        }
    ]
}
```

我们可以看到，最外面是一对花括号`{}`，其中又出现了花括号和方括号`[]`。许多位置采用了`"名称": 内容`的写法，有些行末带有逗号，有些则没有。冒号左侧的名称总是带着双引号，右侧的内容却有多种形式：`2`是数字，`"教程行为包"`是一段文本，而`header`和`modules`后面的内容还进一步分出了层次。

这几个观察，恰好对应了我们需要解决的问题：不同的括号表示什么？冒号怎样把两部分数据联系起来？逗号在何时出现？一份数据里面又为什么可以放入另一份数据？下面，我们来一一认识。

## 对象与它的成员

由一对花括号包围的结构称为**对象**（**Object**）。对象可以用来描述一组带名称的数据。例如，我们希望记录一位名叫小明的学员的姓名、身高和体重，可以写成：

```json
{
    "name": "小明",
    "height": 170,
    "weight": 60
}
```

这里约定身高以厘米为单位，体重以千克为单位。`"name": "小明"`是对象中的一个**成员**（**Member**），也常被称为一个**字段**（**Field**）。冒号左侧的`"name"`是成员的名称，通常称为**键**（**Key**）；右侧的`"小明"`是**值**（**Value**）。这个成员表达的关系便是：在我们约定的`name`属性下，记录的内容为“小明”。另外两个成员分别记录身高和体重。

键必须采用字符串的形式，也就是这里带双引号的写法；值则可以使用JSON允许的不同类型。键叫什么，并不是JSON语法预先规定的。本例中的`name`、`height`和`weight`由我们自己约定，而附加包中的字段名需要遵守游戏对应文件的要求。把清单中的`header`改成`head`，仍然可能得到语法正确的JSON，却已经改变了游戏查找的字段。

对象的每两个相邻成员之间使用一个半角逗号`,`分隔。因此，前两个成员后面有逗号，最后一个成员之后没有逗号。**逗号的作用是分隔成员，而不是标记一行已经结束。** 即使把三个成员写在同一行，分隔关系也不改变：

```json
{"name":"小明","height":170,"weight":60}
```

如果对象中暂时没有任何成员，可以写成`{}`，称为**空对象**（**Empty Object**）。对象中的键也允许是空字符串。例如，下面的写法符合JSON语法，只是我们通常需要更明确的字段名来表达含义：

```json
{"": "没有另取名称的记录"}
```

对象通过名称区分成员，而不是通过成员排在第几位区分属性。对于这份学员记录，把`weight`移到`name`前面，不会使体重变成姓名。我们仍然应该保持统一的书写顺序，方便人阅读，但不应把对象键的排列当作通用的执行次序。

还需要特别留意同一对象中的重名。下面的文本中，`name`出现了两次：

```text
{"name": "小明", "name": "小红"}
```

这与少写逗号不同：JSON的语法形式并没有直接排除重名，但[RFC 8259第4节](https://www.rfc-editor.org/rfc/rfc8259.html#section-4)建议对象内的名称保持唯一。不同读取器可能只保留最后一项、报告错误，或保留重复记录。我们不应该依赖其中某一种行为。本例如果只记录一位学员，就保留一个`name`；如果需要记录两位学员，则应使用接下来介绍的数组。

## 数组把数据按顺序放在一起

**数组**（**Array**）使用一对方括号包围一串有顺序的值，每个值称为一个**元素**（**Element**）。例如，一组学员姓名可以写成：

```json
["小明", "小红", "小华"]
```

数组中的元素之间同样使用逗号分隔，最后一个元素之后不再添加逗号。与对象相比，数组不要求为每个元素单独取名，而是保留它们的排列顺序。因此，这三个姓名组成的数组与顺序颠倒后的数组不同。

在JavaScript及本教程后续常见的编程接口中，我们使用从0开始的**索引**（**Index**）表示元素的位置：小明的索引为0，小红为1，小华为2。这是访问数组时的约定，不意味着我们要在JSON里把`0:`、`1:`写到姓名前面。

数组也可以为空，写成`[]`。从JSON语法上说，同一个数组允许放入不同类型的值，例如：

```json
["小明", 170, true, null, {"score": 90}, [1, 2]]
```

其中一些类型我们稍后再解释。现在先注意：数组既可以容纳简单的值，也可以容纳对象或另一个数组。不过，语法允许这样组合，不等于每个游戏字段都接受这种组合。

回到开篇清单，`version`对应`[1, 0, 0]`，其中三个位置分别承担版本号的不同部分，不能随意交换。`modules`对应的数组则容纳模块对象。数组即使只有一个模块，也仍然要保留方括号；“一个元素的数组”和“那个元素本身”是两种不同的结构。

## 字符串怎样保存文本

**字符串**（**String**）由半角直双引号`"`包围，用来记录一段文本。名字、说明、文件路径和许多标识符都是字符串。我们可以直接在字符串里使用中文，不需要把中文全部转换成别的形式：

```json
{
    "name": "小明",
    "note": "",
    "height_text": "170厘米",
    "number_text": "170",
    "number_value": 170
}
```

`note`的值是两个紧邻的双引号，称为**空字符串**（**Empty String**），表示长度为0的文本。`"170"`虽然看起来全是数字，仍然是字符串，与数字`170`属于不同的类型。读取程序可以对它们作出不同处理，我们不能仅凭显示出来的字符相似，就随意增删引号。

用来标记字符串边界的必须是半角直双引号。单引号`'`和中文弯引号`“”`不能替代它，但中文弯引号可以作为字符串内部的普通文本。例如`"他说：“开始吧。”"`便是合法字符串。

### 双引号、反斜杠与换行

如果文本本身需要包含一个半角双引号，直接写入会与字符串的结束位置混淆。这时需要使用**转义**（**Escape**），在双引号前加一个反斜杠：

```json
{
    "message": "请打开\"教程行为包\"。",
    "path": "C:\\Tutorial\\manifest.json",
    "two_lines": "第一行\n第二行",
    "literal_backslash_n": "\\n"
}
```

第一个值中的`\"`表示文本里的双引号，所以读取到的消息是`请打开"教程行为包"。`。第二个值中的`\\`表示一个反斜杠，读取到的路径才是`C:\Tutorial\manifest.json`。第三个值中的`\n`表示换行字符；第四个值则先用`\\`得到一个反斜杠，再接普通字母`n`，因此它记录的是两个字符`\`和`n`，不会换行。

JSON允许的转义形式是确定的，不能因为希望保留某个字符，就随意在它前面加反斜杠：

| JSON文本中的写法 | 读取后表示的字符 |
| --- | --- |
| `\"` | 半角双引号 |
| `\\` | 反斜杠 |
| `\/` | 正斜杠；普通的`/`也可以直接写入 |
| `\b`、`\f` | 退格符、换页符 |
| `\n`、`\r`、`\t` | 换行符、回车符、水平制表符 |
| `\u`后接四个十六进制数字 | 一个Unicode转义单元 |

例如，`\q`不是JSON转义，`\x41`和`\u{41}`也不是标准JSON中的写法。若希望文本包含反斜杠和字母`q`，应写成`"\\q"`。

字符串内部不能直接包含U+0000至U+001F的控制字符，其中也包括真实的换行和制表符。因此，下面试图把字符串直接跨行写出的文本是错误的：

```text
{"message": "第一行
第二行"}
```

我们应当写成`"第一行\n第二行"`，就像前面的`two_lines`示例。这里要分清“文件为了排版而换行”和“字符串的值包含换行”这两件事，前者出现在字符串外，后者需要正确转义。

### Unicode转义

我们也可以用Unicode转义记录字符。例如，`"\u5C0F\u660E"`和`"小明"`读取后表示同一段文本。每个`\u`后面恰好是四位十六进制数字，其中的A至F可以使用大写或小写。

对于基本多文种平面以外的字符，若采用这种转义写法，则需要一对UTF-16**代理项**（**Surrogate**）。例如，下面两个字符串都表示同一个笑脸字符：

```json
["😀", "\uD83D\uDE00"]
```

初学时无需手工计算代理对，通常直接输入字符，并将文件保存为UTF-8即可。需要了解这一点，是为了避免把一对转义从中间截断。某些解析器能够接受孤立的代理项转义，但这类内容无法形成正常的Unicode字符，跨程序处理时可能出现问题。我们应让文本工具完整地保存字符，而不是把“解析器没有报错”当作字符数据一定完整的证明。

## 数字的写法与精度

JSON中的**数字**（**Number**）采用十进制写法，可以是整数、小数，也可以带指数：

```json
[0, -3, 170, 60.5, 0.25, -0.5, 1e3, 2.5E-2, 1e+2]
```

这里的`1e3`表示1000，`2.5E-2`表示0.025。指数部分的`e`可以大写，也可以小写；`e`或`E`后面的指数数字前可以有正负号。不过，整个数字最前面只允许可选的负号，不能加正号。

我们可以用几个容易混淆的写法检验这条规则：

| 错误写法 | 错误原因 | 可以采用的写法 |
| --- | --- | --- |
| `+3` | 整个数字前不允许正号 | `3` |
| `03` | 非零整数部分不允许前导零 | `3` |
| `.5` | 小数点前缺少整数部分 | `0.5` |
| `1.` | 小数点后缺少数字 | `1.0` |
| `1e` | 指数部分缺少数字 | `1e0` |
| `0x10` | 不能使用十六进制前缀 | `16` |
| `1_000` | 数字内部不能使用下划线分隔 | `1000` |

`NaN`、`Infinity`和`-Infinity`也不属于标准JSON数字。另一方面，`1e400`在数字语法上成立，却未必处在实际读取器能够表示的范围内。这说明**数字怎样写**与**程序能把它保存得多精确**是不同的问题。

JSON没有要求所有程序都用同一种整数或浮点类型保存数据。很多程序使用IEEE 754双精度浮点数；在这种实现下，从`-9007199254740991`到`9007199254740991`的整数构成常用的安全整数范围。超出这个范围，并不是每个整数都会立刻失真，而是不能再保证相邻整数都可以准确区分。小数也有类似的精度限制，例如0.1通常不能被二进制浮点数精确表示。

因此，身份证号式的长编号、需要保留前导零的编码等内容，若本质上用来标识对象而非计算，通常适合按照双方约定保存为字符串。对于Minecraft已有字段，则必须服从字段规定的类型，不能为了避免精度问题就自行把所有数字加上引号。

## 布尔值与空值

有些信息只有“是”或“否”两种状态，例如一位学员是否完成了练习。这时可以使用**布尔值**（**Boolean Value**）：`true`表示真，`false`表示假。另有一种值`null`，称为**空值**（**Null**），可由使用数据的双方约定为“尚无记录”等状态。

```json
{
    "name": "小明",
    "has_finished": true,
    "needs_help": false,
    "score": null
}
```

我们在这个示例中约定：小明已经完成练习，目前不需要帮助，但成绩尚未登记。这个约定来自我们的数据设计，JSON本身并不知道“成绩未登记”是什么意思。换到别的文件中，`null`也可能承担其他含义，或者根本不被允许使用。

这三个固定写法都必须小写，也不带引号。`True`、`FALSE`、`None`和`NULL`都不是标准JSON的对应写法。`"false"`则是一个合法字符串，但它并不因此成为布尔值`false`。

空值还需要与其他几个“看起来没有内容”的状态区分：

```json
{
    "score": null,
    "mistake_count": 0,
    "has_passed": false,
    "note": "",
    "answers": [],
    "extra": {}
}
```

其中`0`是一个确定的数字，`false`是一个确定的真假状态，`""`是空文本，`[]`是没有元素的数组，`{}`是没有成员的对象，而`null`是另一种独立的值。它们不能任意互换。

同样，`{"score": null}`与`{}`也有区别：前者明确存在`score`这个键，只是值为空；后者没有这个成员。在某个游戏格式中，省略字段可能意味着使用默认设置，而写入`null`可能导致类型不符。究竟如何处理，由那个格式规定，不能从“空”这个日常用语推断。

## 嵌套、根值与空白

到这里，我们已经认识了JSON的六类值：对象、数组、字符串、数字、布尔值和空值。对象的成员值和数组的元素都可以继续使用这些类型，由此形成**嵌套**（**Nesting**）。我们把前面分散的信息组合起来：

```json
{
    "class_name": "附加包入门",
    "students": [
        {
            "name": "小明",
            "has_finished": true,
            "scores": [90, 95]
        },
        {
            "name": "小红",
            "has_finished": false,
            "scores": []
        }
    ]
}
```

我们先进入最外层对象，找到`students`；它的值是数组，里面有两个对象，每个对象又有自己的`name`和`scores`。两位学员都使用`name`作为键，并不构成前面所说的重复键，因为它们分属两个不同的对象。键的唯一性应当在同一对象内判断。

花括号和方括号要按照嵌套关系闭合，而不是只要总数相等就行。上例中需要先结束第二位学员的对象，再结束学员数组，最后结束最外层对象。把这几个括号倒过来，即使数量没变，也破坏了数据的结构。

一份标准JSON文本包含一个完整的**根值**（**Root Value**）。根值可以是对象或数组，也可以直接是其他类型。例如，单独保存下面的数字，就是语法成立的一份JSON文本：

```json
170
```

单独的`"小明"`、`true`或`null`也同样成立。不过，Minecraft清单要求的是具有指定结构的对象，所以不能用这个数字替代清单。把两个完整对象直接并排写入一个文件，也不能得到一个标准JSON文本：

```text
{"name": "小明"}
{"name": "小红"}
```

如果需要在同一份JSON中记录两者，可以把它们放到一个数组里：

```json
[
    {"name": "小明"},
    {"name": "小红"}
]
```

为了让嵌套容易阅读，我们在同一层级使用相同的**缩进**（**Indentation**）。本教程通常每深入一层增加四个空格。缩进不会替代括号，也不会替代逗号，它只是把原本已经存在的结构更清楚地展示出来。

JSON允许用作结构之间**空白**（**Whitespace**）的字符只有普通空格、水平制表符、换行符和回车符。它们可以出现在值的前后和相应结构符号之间，但不能插到一个数字或`true`的中间。全角空格等其他看似空白的字符，不应拿来替代这些结构空白。

还要注意字符串内部的空格属于数据。`"小明"`与`" 小明 "`不相同，`"tutorial:token"`与`"tutorial: token"`也不相同。使用编辑器格式化JSON可以整理结构周围的排版，我们却不能自行删除字符串内部的所有空格来“压缩文件”。

## JSON、JavaScript与带注释的写法

我们现在再回头看JSON的名称。虽然它源于JavaScript的对象写法，但一份JSON数据并不是一段JavaScript程序。下面这段可以用作JavaScript代码，却不是标准JSON：

```text
const settings = {
    name: '教程',
    count: 1 + 2,
};
```

其中包含变量声明、没有双引号的键、单引号字符串、算术表达式和尾逗号，这些都不是这里允许的JSON写法。如果只是想把名称和计算结果保存为数据，应写成：

```json
{
    "name": "教程",
    "count": 3
}
```

标准JSON也不能直接存放函数、`undefined`或循环引用。字符串中即使写了`"1 + 2"`，读取后也只是文本，不会自动求值。以后学习脚本时，我们会使用相应的解析与生成接口，在程序内的数据和JSON文本之间转换；这与直接执行一段代码是不同的过程。

另外，我们可能在工具配置或部分附加包资料中看到**注释**（**Comment**）。`//`后直到行末的内容是常见的单行注释，`/*`与`*/`之间则是块注释。但**标准JSON不允许注释**。下面展示的是带注释的扩展写法，不是可以交给任意JSON读取器的标准JSON：

```text
{
    // 显示给读者的名称
    "name": "教程",
    "count": 3 /* 初始数量 */
}
```

去掉注释之后，它便成为上一个有效示例。人们常把带注释的JSON称为**JSONC**（**JSON with Comments**），但是不同工具究竟还支持哪些扩展，需要分别确认。支持注释，并不自动意味着所有读取器都支持尾逗号、单引号或其他JavaScript语法。

例如，Visual Studio Code具有JSON和JSON with Comments两种语言模式。将编辑器切换成后者，只是改变编辑器怎样检查当前文本，不会使Minecraft或其他程序自动接受同样的扩展。我们在本教程中优先编写不带注释的标准JSON，并把解释放在示例外面；确有特殊格式要求时，再针对具体文件说明。

## 将文件保存下来，并学会定位错误

现在，我们可以新建一个练习文件，将最开始的清单完整写入，再以`manifest.json`为名保存。JSON文件是纯文本文件，不需要使用文字处理软件的文档格式；还应检查真实文件名，避免在系统隐藏扩展名时保存成`manifest.json.txt`。

文件编码选择**UTF-8**。RFC 8259要求非封闭系统之间交换的JSON使用UTF-8，并规定网络传输的JSON不应添加**字节顺序标记**（**Byte Order Mark**，**BOM**）；解析器可以选择忽略已有BOM，但不保证每个工具都会这样处理。我们的新文件统一保存为不带BOM的UTF-8，便于不同工具读取。这里的BOM处理与字符串中正常保存一个字符，是不同层面的问题。

在支持JSON的编辑器里，先确认语言模式，再使用“格式化文档”观察缩进和括号是否成对。例如，Visual Studio Code可以在命令面板或上下文菜单中执行这一操作，也会为识别到的错误标出位置。

不过，报错位置经常是解析器“终于无法继续”的位置，并不一定是最初写错的位置。下面的文本漏掉了一个逗号：

```text
{
    "name": "小明"
    "height": 170
}
```

错误可能标在`height`附近，因为读取器在完成第一个成员之后，期待看到逗号或对象结束符，却遇到了另一个键。此时应回看上一项的末尾，修正为：

```json
{
    "name": "小明",
    "height": 170
}
```

如果报错出现在文件末尾，则可以检查是否漏掉了引号或闭合括号。遇到一连串错误时，先修正靠前、最能解释后续错误的一处，再重新查看提示；不要只为了清除红线而不断往末尾添加括号。

语法检查通过之后，还要继续检查具体文件格式。有些编辑器可以依据**JSON模式**（**JSON Schema**）提示字段名和类型，例如某个字段应为数组、某个数字不能为负。模式描述的是特定数据的要求，不会把所有语法正确的JSON都变成有效清单。最终还应在游戏中检查包能否加载、功能是否达到预期。

## 亲手修正一份练习

下面的记录有几处语法问题。请先在编辑器中逐一定位，再与后面的写法比较：

```text
{
    'name': "小明",
    "level": 01,
    "has_finished": True,
    "scores": [90, 95,],
    "note": "请打开\"教程\"。",
}
```

第一处是`name`使用了单引号；第二处是数字`01`包含前导零；第三处是布尔值`True`的首字母大写；第四处是数组最后一个元素后面的逗号；第五处是对象最后一个成员后面的逗号。`note`中的双引号已经正确转义，不需要“修正”为另一个值。保留原本想表达的数据，可以得到：

```json
{
    "name": "小明",
    "level": 1,
    "has_finished": true,
    "scores": [90, 95],
    "note": "请打开\"教程\"。"
}
```

接下来，再尝试完成三个小改动：

1. 为记录增加`next_score`，并约定`null`表示下一次成绩尚未登记。检查新增成员前后应该在哪里加逗号。
2. 将`scores`改成空数组，再比较它与`null`、以及完全省略`scores`成员的区别。
3. 回到开篇清单，找出`header`的值、`modules`的第一个元素，以及该元素内部的`version`。试着只移动排版、不改变数据，确认自己能看清每一层结构。

第一项需要增加`"next_score": null`；第二项仍然保留一个数组，只是其中没有成绩元素；第三项则依次对应对象、对象和数组。如果这三个答案已经清楚，大家便能继续理解清单中“包的信息”与“模块的信息”为何要放在不同层次中。
