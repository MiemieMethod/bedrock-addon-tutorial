# 测试与打包

到这里，我们已经编写了清单和配方。接下来，我们把行为包交给游戏读取，并验证每一步是否符合预期。只有编辑器不再提示语法错误，还不能说明附加包已经完成；只有出现“导入成功”，也不能说明配方已经正确运行。

## 将行为包放入开发目录

**开发目录**（**Development Folder**）是供开发者反复修改和测试包内容的位置。对于当前Windows正式版客户端，可以在资源管理器地址栏中输入：

```text
%appdata%\Minecraft Bedrock\users\shared\games\com.mojang
```

其中`development_behavior_packs`用于放置开发中的行为包，`development_resource_packs`用于放置开发中的资源包。将整个`Tutorial_BP`文件夹复制到前者，确保清单的位置是`development_behavior_packs/Tutorial_BP/manifest.json`，而不是在两个连续的`Tutorial_BP`文件夹里面。

Windows较早的UWP安装使用过`%localappdata%\Packages\Microsoft.MinecraftUWP_8wekyb3d8bbwe\LocalState\games\com.mojang`路径。不要因为旧教程中的路径存在，就认定当前启动的游戏仍在读取它。正式版和预览版也可能使用不同的数据目录。最可靠的判断是：在当前游戏中建立一个测试世界，确认正在使用的安装及其数据位置，再按该安装的官方说明放入包。

如果所在平台无法方便地访问开发目录，可以使用本节后面介绍的`.mcpack`导入方式。两种方式的包内容相同，只是送入游戏的方法不同。为避免混淆，测试同一个UUID时尽量只保留一种来源，不要同时放着开发副本和多个导入副本。

## 建立可以重复使用的测试世界

我们新建一个专门用于本教程的世界，在世界设置的“行为包”页面找到“教程行为包”，将它激活。名称应当与上一节清单中的`header.name`一致。当前练习不需要实验性功能；如果只是为了准备测试材料，可以使用创造模式，也可以在自己允许作弊的测试世界中使用命令。

进入世界后，我们依次观察三个结果：

1. 包出现在可用列表中，说明游戏至少识别了清单。
2. 包位于该世界的已激活列表中，说明我们选择了让这个世界使用它。
3. 在工作台中按照上一节的图案放入八块圆石，结果格出现四块石头，取出时原料按预期消耗，说明配方的主要功能达到了预期。

这三步不能相互代替。如果只验证了第一步，便把包发给别人，遗漏激活或定义错误的问题仍然可能留在作品中。

我们还可以停用行为包后重新进入测试世界，使用相同图案再试一次。自定义配方应当不再出现。这样便能排除测试世界里另一个包恰好提供相同配方的情况。

## 通过内容日志定位问题

游戏的创作者设置中提供**内容日志**（**Content Log**）相关选项。不同版本的界面位置和名称可能略有变化，我们找到相应选项后，开启日志显示或文件记录，再重新加载测试世界。日志中通常会给出发生问题的文件、标识符或字段，这是比反复重新导入更有效的线索。

| 观察到的现象 | 优先检查的位置 |
| --- | --- |
| 包列表中没有这个包 | 当前游戏的数据目录、清单文件名、压缩层级和清单语法 |
| 包显示缺少依赖 | 清单依赖中的包UUID与版本，以及被依赖包是否存在 |
| 包已激活但配方无效 | 配方目录、标识符、物品名称、图案和内容日志 |
| 手动合成成功但配方书未显示 | 解锁条件、世界的配方规则、界面筛选状态 |
| 修改文件后仍是旧效果 | 是否改了正在加载的副本、是否重新进入世界、是否存在重复UUID |

修改后先保存编辑器中的文件，再退出并重新进入世界。若涉及清单或资源缓存，完整退出并重新启动游戏是更清晰的复核办法。不要假定所有类型的文件都能通过同一种热重载操作即时更新。

## 打包为可导入文件

当开发目录中的版本满足预期后，我们便可以将它打包成**包文件**（**Pack File**），扩展名为`.mcpack`。它本质上是ZIP格式的归档，关键是清单必须直接位于归档根目录。

在Windows中，我们可以先进入`Tutorial_BP`文件夹，选中其中的`manifest.json`和`recipes`文件夹，将这些内容压缩为ZIP，再把扩展名改为`.mcpack`。也可以在工作目录中使用PowerShell：

```powershell
Compress-Archive -Path .\Tutorial_BP\* -DestinationPath .\Tutorial_BP.zip
Rename-Item .\Tutorial_BP.zip Tutorial_BP.mcpack
```

运行前应确认目标ZIP和MCPACK不存在；反复打包时可以另取名称保存修订版。完成后，用压缩软件检查归档，第一层应该能直接看到`manifest.json`，不能只看到一个包着所有内容的`Tutorial_BP`文件夹。然后打开`.mcpack`，将其导入Minecraft，再在新建的测试世界中重新激活和验证。

为了确保这次测试读取的是导入文件，我们可以先退出游戏，把开发目录中的同UUID副本移回自己的工作目录。不要删除尚未备份的源文件。发布更新时，保留UUID，提高包与模块版本；若资源包依赖了这个版本，也要同步更新依赖项。

当一个作品同时包含资源包和行为包时，可以分别制作两个`.mcpack`，再将它们归档为ZIP并使用`.mcaddon`扩展名。这便于一次导入两个包，但不会替代清单中的依赖关系。导入之后仍然要检查两个包是否都正确参与世界。

至此，我们完成了“编辑—加载—观察—对照—打包—重新导入”的一个循环。后面无论制作实体、粒子还是脚本，都可以沿用这个过程，将每次新增功能控制在容易验证的范围内。
