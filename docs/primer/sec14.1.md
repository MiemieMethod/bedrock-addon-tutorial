# 发布至MCPEDL

当我们的附加包能够在开发环境中运行后，接下来便是让其他玩家顺利获得并使用它。**MCPEDL**是面向基岩版社区的作品发布网站。本节将一起整理发布文件和作品说明，并了解提交审核前需要完成的检查。发布页面应当帮助玩家判断作品是否适合自己，也应当帮助我们在收到问题时定位原因。

## 先准备真正的发布文件

开发目录中可能包含编辑器工程、测试素材、临时日志和旧版本文件。它们不一定都应出现在最终作品中。我们先建立独立的发布目录，只放入游戏运行需要的内容，并保留许可证、必要的使用说明和素材署名。

根据作品类型选择分发格式：单个资源包或行为包通常使用`.mcpack`；同时提供多个包可以组织为`.mcaddon`；已经布置好的地图使用`.mcworld`；需要从同一起点反复创建世界则使用`.mctemplate`。文件扩展名只告诉客户端怎样尝试导入，内部结构仍然必须正确。

第一次发布前，把制作好的文件重新导入另一份测试环境。这里要测试的是玩家将下载到的压缩包，而不只是开发目录。尤其要检查是否遗漏纹理、声音、脚本入口，以及是否错误引用了只存在于作者电脑上的资源。

## 为版本留下可以核对的记录

不妨把首次公开版本命名为`researcher_addon-1.0.0.mcaddon`。文件名用于识别发布物，清单中的版本则用于游戏的包管理，两者最好保持可理解的一致关系。

我们还可以记录文件的SHA-256，用来核对玩家拿到的文件是否与这一版发布物一致。在PowerShell中，可以这样计算：

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath '.\researcher_addon-1.0.0.mcaddon'
```

哈希值只能证明文件字节是否相同，不能证明作品没有漏洞。生成哈希之后若再次修改文件，就需要重新计算。将同一个版本号不断替换为不同内容，会使问题反馈难以对应，因此正式更新时应增加版本并保留更新记录。

## 写出玩家需要的说明

我们先回答三个问题：这个作品增加什么？玩家怎样开始使用？它在哪些条件下经过测试？不要让玩家从十几张截图中猜测启用方式。

可以按照下面的结构整理自己的发布说明：

```text
作品名称与版本：
主要功能：用两三句话说明玩家能够实际做什么。
开始方式：导入后需要启用哪些包，第一步怎样取得物品或进入玩法。
测试环境：写明游戏完整版本、正式版或预览版、设备及多人测试情况。
所需设置：列出确实需要的实验开关；不需要时也明确说明。
已知限制：记录尚未支持的平台、冲突或未解决问题。
更新内容：与上一版相比新增、修改和修复了什么。
问题反馈：提供作者愿意维护的反馈入口。
素材与许可：列出第三方素材来源、作者及许可要求。
```

这是一份填写结构，不应把没有测试过的项目写成“全部支持”。例如，我们只在Windows正式版完成了单人测试，就应如实说明；预览版能导入，也不能自动推定正式版能够使用相同的新组件。

截图应展示当前版本的真实内容，至少包含一个主要功能场景和必要的启用步骤。若截图使用了其他光影或纹理包，应在说明中标明，避免让玩家把那些效果误认为本作品的一部分。

## 提交作品并处理审核意见

登录自己用于创作的MCPEDL账户，从作者提交作品的入口创建条目。网站的菜单和表单可能更新，我们应以实际页面为准，依次填写名称、分类、介绍、兼容版本、图片和下载信息，不必依赖旧截图中的按钮位置。

提交前阅读网站当期的Moderation Guidelines。我们读取的规则要求作品内容真实、素材来源与授权明确，并对第三方安装程序和下载跳转过程作出限制。最容易维护的做法是提供清楚直接的发布文件，而不是要求玩家先安装不相关的软件。

如果审核要求修改，应逐条对应反馈完善，再提交复审。例如，“缺少玩法说明”应通过补充开始步骤解决；“下载链接失效”应当实际检查链接；不能只改一个标题后反复提交相同内容。审核通过也不等于网站替我们完成了全部兼容性测试。

## 更新之后怎样收集问题

玩家反馈“不能用”时，我们至少需要确认游戏版本、设备、包版本、启用设置、复现步骤和内容日志。可以在发布页面给出简短的反馈格式，让玩家一次提供必要信息。

若问题仅出现在升级后的旧世界中，应区分新世界正常、旧世界异常这两种情况。若新版本删除或重命名了标识符，还应提供迁移说明，而不是要求所有玩家自行猜测丢失物品的原因。

发布前最后从玩家角度走一遍流程：打开介绍，下载文件，导入游戏，启用内容，完成第一次操作。如果在任何一步需要作者私下补发文件或额外解释，就应把相应内容补进发布物或说明中。
