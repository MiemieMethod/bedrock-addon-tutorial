# 认识清单文件

上一节中，我们已经为第一个行为包准备了文件夹。接下来，我们在`Tutorial_BP`的根目录中新建`manifest.json`，然后用文本编辑器打开它。注意检查完整文件名，尤其不要在隐藏了文件扩展名的情况下创建出`manifest.json.txt`。

## 编写第一个清单

我们先完整地观察下面的清单，再逐项理解其中的内容：

```json
{
    "format_version": 2,
    "header": {
        "name": "教程行为包",
        "description": "从一个新的合成配方开始。",
        "uuid": "88d1db72-bbea-4f17-9671-409c60c40972",
        "version": [1, 0, 0],
        "min_engine_version": [1, 21, 0]
    },
    "modules": [
        {
            "type": "data",
            "uuid": "21a0b5ca-a7c7-4860-86a9-09bfa64e3c15",
            "version": [1, 0, 0]
        }
    ]
}
```

这是一个普通的JSON对象，包含`format_version`、`header`和`modules`三个字段。大家可以直接将其写入文件，用来完成本教程的练习。不过，在制作自己的独立作品时，应该重新生成其中的两个UUID，不能让所有作品一直共用示例中的标识。

**头**（**Header**）描述包本身的信息。这里的`name`和`description`分别决定包的名称和简介；`uuid`则是包的身份。**模块**（**Module**）用来说明包提供的功能，所以`modules`是一个数组，数组中的每个对象描述一个模块。我们目前只需要一个类型为`data`的模块，即行为包的数据模块。如果这里写成`resources`，它便会成为资源模块，也就不能按我们的预期读取配方了。

## 三种版本不能混淆

我们可以看到，这个很短的文件已经出现了三种与版本有关的字段：

| 字段 | 本例的值 | 描述的对象 |
| --- | --- | --- |
| `format_version` | `2` | 清单文件使用的格式 |
| `version` | `[1, 0, 0]` | 我们自己编写的包或模块的版本 |
| `min_engine_version` | `[1, 21, 0]` | 包所要求的最低引擎版本，并参与部分版本兼容行为的选择 |

**格式版本**（**Format Version**）回答的是“游戏应当按哪一种清单格式来读这个文件”。它与下一节配方文件中的格式版本相互独立，不能因为配方写了`"1.20.10"`，便把清单中的`2`一起改成这个字符串。

包的`version`由我们自己管理。开发一个修订版时，可以将它从`[1, 0, 0]`提高为`[1, 0, 1]`。游戏据此区分同一UUID的不同版本；反复导入内容已经变化、版本却完全相同的包，很容易把缓存或重复导入的问题误认为代码错误。

`min_engine_version`也不是“我们电脑当前安装的版本”的自动记录。这里选用`[1, 21, 0]`作为基础练习的保守门槛，并不表示1.21.0是当前最新版本，也不能仅凭这个值就保证作品在此后所有版本都经过测试。以后加入更晚才提供的功能时，应当结合该功能文档调整最低版本，并在所承诺支持的版本中测试。

## UUID的作用

**通用唯一标识符**（**Universally Unique Identifier**，**UUID**）用于让游戏区分不同的包和模块。包的名字可以相同，但身份不能因此相同。我们可以使用UUID生成器，也可以在Windows PowerShell中运行：

```powershell
[guid]::NewGuid().ToString()
```

连续运行两次，将两个不同的结果分别填写到`header.uuid`和模块的`uuid`中。不要将头部的UUID再次复制到模块里。

这里还有一个容易混淆的地方：**发布同一作品的更新时，保留包和模块的UUID，提高版本；从这个作品复制出一个独立的新作品时，生成新的UUID。** 如果每次修改一行代码就换UUID，游戏便可能把每个修订都看成一个全新的包。

## 当行为包需要资源包时

我们的配方只使用原版物品，所以暂时不需要资源包依赖。以后制作自定义实体时，行为包可能需要另一个资源包提供模型和纹理。这时可以在清单顶层增加**依赖**（**Dependency**）：

```json
{
    "dependencies": [
        {
            "uuid": "0b03ed47-759e-42bf-bc72-d5a36ba90c83",
            "version": [1, 0, 0]
        }
    ]
}
```

上面只展示需要补充的字段，不能用它替换整个清单。这里填写的是被依赖资源包的`header.uuid`和`header.version`，不是它的模块UUID。我们也不必为了“看起来完整”而让两个包相互依赖；依赖应反映实际需要，本教程后面采用行为包依赖资源包的单向关系。

## 检查清单

保存之后，我们先让编辑器检查JSON语法，再逐项核对：根目录中是否正好有`manifest.json`，模块类型是否为`data`，两个UUID是否不同，版本是否为包含三个整数的数组。下一节补充配方，随后便可以在游戏中观察本节填写的名称和简介。

如果包没有出现，首先检查文件名与目录层级；如果出现了“缺少依赖”，检查是否误加了并不存在的依赖；如果显示了包但配方没有效果，则继续检查配方本身，不能只修改清单里的版本号来碰运气。
