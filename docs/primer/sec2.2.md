# 认识行为包

上一节中，我们认识了为客户端提供资源的资源包。接下来，我们重新观察已经制作过的**行为包**（**Behavior Pack**），看看一个配方之外，它还能够承载哪些内容。

## “行为”并不只是生物的动作

我们日常所说的“行为”，很容易让人想到走路、攻击和逃跑。不过，行为包中的“行为”具有更广的范围：一份合成配方规定原料与产物之间的关系，一份战利品表规定掉落如何抽取，一份地物规则规定世界生成时何处放置内容。这些都在描述游戏的规则或数据，而不只是描述生物的动作。

| 行为包中的位置 | 内容示例 |
| --- | --- |
| `recipes` | 合成、烧炼等配方 |
| `entities` | 服务端实体定义，注意这里使用复数 |
| `items`、`blocks` | 自定义物品和方块的定义 |
| `loot_tables`、`trading` | 战利品表与交易表 |
| `spawn_rules` | 实体自然生成规则 |
| `functions` | 由命令组成的函数文件 |
| `structures` | 可供加载的结构文件 |
| `features`、`feature_rules` | 地物及其放置规则 |
| `scripts` | 按清单入口加载的脚本，常用目录名为`scripts` |

最后一项需要特别说明：脚本入口由清单中的脚本模块指定，不是新建一个`scripts`文件夹就会自动执行其中的全部文件。类似地，放入一份战利品表也不意味着所有生物立即改用这张表，它通常还需要由实体等内容引用。

## 用第二个配方观察“新增”

我们回到第一章的`Tutorial_BP`，保持已经编写的清单和圆石配方不变，再新建`recipes/sticks_from_bamboo_pair.json`：

```json
{
    "format_version": "1.20.10",
    "minecraft:recipe_shapeless": {
        "description": {
            "identifier": "tutorial:sticks_from_bamboo_pair"
        },
        "tags": ["crafting_table"],
        "ingredients": [
            {"item": "minecraft:bamboo"},
            {"item": "minecraft:bamboo"}
        ],
        "unlock": [
            {"item": "minecraft:bamboo"}
        ],
        "result": {
            "item": "minecraft:stick",
            "count": 2
        }
    }
}
```

这里使用的是**无序配方**（**Shapeless Recipe**）。与有序配方不同，它通过`ingredients`列出原料，不再使用`pattern`和`key`描述位置。我们把两根竹子分别放在合成格中的两个格子里，位置可以任意选择。

原版本来就有竹子合成木棍的规则。为了观察这个新配方，测试时先将两根竹子横向放在相邻的两个格子里，避开原版纵向排列的配方。按照本例，结果应当为两根木棍；若使用与原版重合的排列，则同时涉及多个配方的匹配关系，不适合作为第一个验收条件。

我们之所以为新文件使用`tutorial:sticks_from_bamboo_pair`，便是为了增加一条属于自己的规则，而不是有意替换某条原版规则。**文件名用于组织文件，定义中的标识符用于识别内容，两者不能混为一谈。** 把文件名改为`my_recipe.json`不会自动修改配方的身份。

这个例子也说明，新增内容仍然可能在玩法层面与原版发生交集。完成验证后，可以移除这条用于观察的配方，避免把练习中的额外产量直接带入正式作品。

## 单人游戏也有两端的分工

即使我们没有加入多人服务器，游戏仍然需要区分客户端表现与世界逻辑。客户端负责显示画面、播放声音等工作；服务端一侧维护世界规则，并决定许多操作的结果。这里的“服务端”是一种职责，不一定意味着另外有一台电脑。

因此，一个仅新增配方的行为包可以不附带资源包，因为结果使用的是原版已有物品。反过来，一个拥有漂亮纹理和模型的资源包，也不会单独给世界增加完整的生物行为。以后设计功能时，我们可以先分别列出“世界应当怎样变化”与“玩家应当看到什么”，再决定文件属于哪一个包。

## 保留清晰的依赖关系

当行为包开始引用自定义资源时，可以按第一章的方法添加对资源包的依赖。激活行为包后，要检查对应资源包是否一并参与世界，而不能只凭依赖字段存在就假定资源内容有效。

遇到错误时，我们也可以沿着关系逐步检查。例如，自定义实体完全无法召唤，应先查看服务端实体标识符和行为包日志；能够召唤但不可见，则进一步检查客户端实体、模型和纹理。两种现象指向不同的问题范围，盲目地把所有文件重命名反而会破坏原本正确的引用。

本节结束时，我们应当能够根据目录找到已制作的两份配方，并说清楚每一份由哪个标识符区分。接下来认识的皮肤包和世界模板具有各自的用途，不能仅通过往行为包里添加一个文件夹便替代它们。
