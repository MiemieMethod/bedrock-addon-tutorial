# 什么是附加包？

在上一章中，我们已经了解了JSON的基本语法，也观察过一个清单文件的示例。不过，当时我们只是将其作为JSON格式的学习材料，并没有进一步讨论它在游戏中究竟起到了什么作用。从本章开始，我们将把这些知识应用到实际的附加包开发中，一起来制作我们的第一个附加包。

在创建文件之前，我们首先需要了解一个问题：我们编写的这些文件，究竟是如何与Minecraft中的游戏内容联系起来的？

## 附加包的概念

**附加包**（**Add-on**）是Minecraft基岩版中用于修改或扩展游戏内容的一种模组形式。通过附加包，我们可以替换方块的纹理、修改生物的行为、添加新的合成配方，也可以进一步制作具有自己的外观和功能的新实体、新物品与新方块。

在开发过程中，附加包通常表现为按照一定结构组织起来的文件夹。文件夹中可能包含JSON文件、纹理图片、声音文件，以及实现某些功能所需的脚本文件。游戏读取这些文件之后，便可以按照其中提供的资源和定义，呈现我们所设计的内容。

这里的“按照一定结构”非常重要。将一张图片随意放入文件夹，并不会让它自动成为某个方块的纹理；同样，编写一个语法正确的JSON文件，也不意味着游戏就能够知道这个文件的用途。我们还需要使用游戏支持的文件格式，将文件放置在规定的位置，并在需要时建立文件之间的引用关系。

换言之，上一章介绍的JSON语法解决的是“如何将数据正确地写出来”的问题，而接下来的教程将进一步解决“应该写入哪些数据，以及如何让游戏使用这些数据”的问题。

## 资源包与行为包

在本教程接下来的开发中，我们最常接触到的是两种包：**资源包**（**Resource Pack**）和**行为包**（**Behavior Pack**）。它们各自负责不同的内容，也可以相互配合，共同组成一个完整的附加包作品。

资源包主要提供游戏表现所需的资源，比如纹理、模型、声音，以及与这些资源有关的客户端定义文件。行为包主要提供游戏内容与行为规则的定义，比如生物的行为、合成配方、战利品表和生成规则。这里的“行为”并不只指生物会做什么动作，也包括物品如何合成、生物被击杀后掉落什么等游戏规则。

为了使两者的区别更加明确，我们不妨考虑这样一个例子：将泥土方块的纹理替换为基岩的纹理。

我们将对应的纹理文件放入资源包，并使游戏正确加载它之后，便可以看到原本的泥土呈现出了基岩的外观。但是，如果我们尝试挖掘这个方块，就会发现它依旧是泥土。它不会因为“长得像基岩”，便自动获得基岩的挖掘性质。这是因为，我们在这个例子中修改的是方块的纹理。**外观发生变化，并不意味着与它对应的游戏规则也发生了变化。**

我们可以将几个简单目标整理如下：

| 我们希望实现的目标 | 主要涉及的包 |
| --- | --- |
| 替换泥土方块的纹理 | 资源包 |
| 替换游戏中某个已有的声音资源 | 资源包 |
| 为已有物品添加新的合成配方 | 行为包 |
| 修改生物的战利品表 | 行为包 |
| 制作同时具有自定义外观和行为的新生物 | 资源包与行为包 |

需要注意的是，并非每个作品都必须同时制作一个资源包和一个行为包。只替换原版纹理时，我们可以从资源包开始；只为已有物品添加配方时，也可以先制作行为包。是否需要两种包共同参与，应当由我们希望实现的功能决定。

## 定义文件与数据驱动

前面已经多次出现了“定义”这个词。**定义文件**（**Definition File**）用于描述游戏中的某种内容，或描述某项功能应当采用的数据。例如，一份配方定义可以告诉游戏：这个配方使用什么原料、原料应当如何排列，以及合成后得到什么物品。在附加包中，许多这样的定义文件都使用JSON格式编写。

在JSON中，我们可以通过键和值描述一个人的名字、身高和体重；在附加包中，我们也可以使用相似的结构描述一个配方。不过，游戏能够识别的键及其含义已经由对应的文件格式规定好了，不能按照自己的喜好随意命名。

这也说明，**JSON语法正确**与**附加包定义正确**是两个不同的要求。一个文件即使不存在括号、逗号或引号方面的错误，仍然可能因为字段名称不正确、值的类型不符合要求，或缺少必要内容而无法达到预期效果。

这种通过提供数据，由游戏读取并执行相应功能的开发方式，被称为**数据驱动**（**Data-Driven**）。随着功能逐渐复杂，我们还会接触到脚本，用于编写更加灵活的逻辑。不过，对于本章的第一个作品而言，我们可以先从简单的数据定义入手。

## 游戏如何识别一个包？

假设我们已经创建了一个文件夹，并准备向其中放入纹理或配方文件，那么游戏如何知道这个文件夹属于什么类型的包，又应该在界面上显示什么名称呢？这就需要使用**清单文件**（**Manifest File**）。

在接下来的教程中，我们将使用名为`manifest.json`的JSON文件，为包提供基本信息。它包含包的名称、描述、标识和版本等内容，也通过模块信息说明这个包提供了哪一类内容。清单文件应当位于对应包文件夹的根目录。其他文件则根据各自的用途，放入相应的位置。

| 文件或内容 | 相对于对应包根目录的位置 |
| --- | --- |
| 清单文件 | `manifest.json` |
| 资源包中的纹理文件 | `textures`目录及其子目录 |
| 行为包中的配方定义 | `recipes`目录 |

大家现在可以新建一个名为`Tutorial`的工作文件夹，再在其中新建`Tutorial_BP`文件夹。`BP`是Behavior Pack的缩写，便于我们自己区分用途；游戏最终仍然通过清单来识别包。暂时保持这个文件夹为空即可，下一节将为它补齐第一个文件。此时游戏还不能将它识别为可用的行为包，这是正常的。

## 从一个简单的目标开始

接下来，我们选择“为已有物品添加一种新的合成配方”作为第一个作品的目标。原料和合成结果都使用游戏中已有的物品，因此暂时无需绘制新纹理，可以将注意力集中在行为包的基本结构、清单文件和配方定义上。

在动手之前，大家也可以尝试回答：一份JSON文件语法完全正确，是否就意味着其中的配方一定能够生效？一个包已经出现在游戏的包列表中，又是否意味着其中的所有内容都已经正确加载？两者的答案都是否定的。我们将在接下来的制作和测试过程中，分别检查包的识别情况和功能的实际效果。

带着这些认识，我们在[下一节](./sec1.2.md)中正式编写清单文件，让游戏先认识我们的第一个包。
