# 认识旧版脚本引擎Script API

在前面的章节中，我们已经能够通过组件、事件和命令组织一些较为复杂的玩法。不过，如果希望为每位玩家分别保存状态，或者将多种游戏事件组合成一套逻辑，仅靠数据文件就会逐渐变得不方便。这时，我们便需要认识**脚本API**（**Script API**）。

在真正编写脚本之前，我们先解决一个容易造成混淆的问题：旧教程中的“Script API”，与现在文档中的“Script API”，是否指的是同一套接口？答案是，我们必须结合接口名称、模块名称和对应的游戏版本来判断，不能只看这个名称。

## 从一段旧代码认识历史接口

大家在阅读较早的基岩版资料时，可能会遇到下面这样的代码：

```javascript
// 历史接口识别示例，不用于本教程的当前示例包。
const tutorialSystem = server.registerSystem(0, 0);

tutorialSystem.initialize = function () {
    // 注册事件监听、组件等初始化工作。
};

tutorialSystem.update = function () {
    // 在系统更新时执行逻辑。
};
```

这段代码最显著的特征是直接使用全局对象`server`，并通过`registerSystem`创建系统。随后，我们将函数赋给系统的初始化、更新等成员。在这一套历史接口中，脚本以系统为组织单位，通过对应的接口访问组件和事件。

这里的`0, 0`属于该历史接口的系统注册约定。它们不是本章稍后将要填写的`@minecraft/server`模块版本，也不表示“安装任意版本的游戏都可以运行”。将这样的代码放进当前脚本包中，不能仅靠修改文件名就使它工作。

因此，本节保留旧版脚本引擎这一主题，主要是帮助我们辨认历史资料和迁移思路。接下来的实际项目使用基于JavaScript模块的接口，并以`@minecraft/server`的`2.0.0`稳定API为最低接口基线。这个基线也不等于“2026年的最新API版本”。

## 将相似的名称分开

我们可以先整理几种经常出现在搜索结果中的写法。

| 资料中的特征 | 阅读时应如何理解 |
| --- | --- |
| `server.registerSystem`、`client.registerSystem` | 较早的基岩版脚本系统，不能直接套用当前模块教程 |
| `mojang-minecraft`、`mojang-gametest` | 模块化脚本早期阶段的名称，应按原文对应版本阅读 |
| `@minecraft/server`、`@minecraft/server-gametest` | 当前模块命名方式，仍须区分具体模块版本和稳定、实验轨道 |
| `mod.server.extraServerApi`等Python导入 | 中国版模组SDK，与本教程的国际版JavaScript接口分别使用 |

这个表并不是说旧资料都没有价值。比如“事件发生后调用回调函数”“保存玩家状态”“将初始化与循环更新分开”等思想仍然可以帮助我们设计程序。但是，接口的拼写、参数、可调用阶段以及支持的平台，都必须重新核实。

尤其需要注意，当前`@minecraft/server`的`1.x`与`2.x`属于模块API的大版本。`1.x`不能因为数字较小，就被等同于本节的`registerSystem`式旧引擎。现代模块接口自身也会进行版本演进。

## 迁移的是功能，而不只是名称

假设一份旧脚本的目标是“玩家进入世界后显示欢迎信息”。我们首先应该把它拆成三个问题：什么情况算进入世界、向谁显示信息、信息是否需要重复显示。把需求拆开之后，再在当前接口中寻找对应的事件和操作。

例如，在后续示例中，我们会使用`world.afterEvents.playerSpawn`监听玩家生成。这个事件还会在重生时发生，所以需要检查事件参数的`initialSpawn`。即便这个值为真，也只表示此次加入过程中的初次生成，不能直接理解为“这位玩家有史以来第一次进入这个存档”。如果要求整个存档中只欢迎一次，还需要额外保存状态。

我们可以看到，真正需要迁移的是事件的含义。把旧事件名替换成一个看起来相似的新事件名，而不检查它的触发条件，往往会使程序虽然没有语法错误，却在重生、重新连接或多人游戏中表现异常。

同样，旧系统的`update`可以启发我们寻找定时执行的入口，但当前脚本中通常使用`system.runInterval`等调度接口。不要将其改写为无限的`while`循环。JavaScript代码需要及时把执行机会交还给游戏；一段长时间不结束的循环会阻塞脚本，并可能触发脚本看门狗的保护。

## 当前模块还需要检查什么？

使用当前模块接口时，我们至少要同时检查三个层面。

首先是**模块依赖**。清单中声明了`@minecraft/server`的哪个版本，就应以该版本公开的接口为依据。编辑器中安装了类型声明，并不会替游戏安装脚本引擎；实际运行接口由对应客户端或BDS提供。

其次是**执行阶段**。在2.x脚本环境中，入口模块的代码可能在世界尚未就绪时运行。此时可以进行允许的事件订阅，却不能随意读取玩家和方块。应将依赖世界状态的工作安排在`worldLoad`、实际游戏事件或合适的调度回调中。我们将在下一节一起建立最小示例。

最后是**稳定性轨道**。不带实验后缀的稳定接口与带`-beta`的接口具有不同的兼容承诺。`internal`类型声明则主要用于认识引擎内部结构，不代表普通附加包获得了调用权限。导出数据中“存在一个名字”，与我们的包“可以使用这个名字”，是两个需要分别验证的问题。

## 如何阅读和排查旧项目

当我们接手一个不能运行的脚本包时，可以按下面的顺序检查：先查看`manifest.json`中的脚本模块与依赖，再查看入口文件的导入语句，然后确认资料中针对的游戏版本。完成这些检查后，才开始定位具体事件和方法。

如果入口使用的是历史全局对象，就将它作为迁移任务处理；如果已经使用`@minecraft/server`，则继续检查大版本、实验接口和执行阶段。这样可以避免在同一份文件中混合三代接口，最后得到一段无法确定运行条件的代码。

至此，我们已经知道本章为什么要先介绍旧版脚本引擎。下一节中，我们将创建一个独立的当前脚本包，亲自观察模块加载、事件订阅和世界就绪之间的关系。
