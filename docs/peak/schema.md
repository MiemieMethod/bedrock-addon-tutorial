# 阅读导出模式

在前面的教程中，我们按照给定格式编写过物品、方块和实体。接下来，我们尝试进一步回答一个问题：当教程没有逐项列出某个组件的全部字段时，应该如何继续研究它？

**模式**（**Schema**）描述了一类数据允许采用的结构。它可以告诉我们某个字段应该是字符串、整数还是对象，也可以给出必要字段和部分数值约束。不过，模式是研究的入口；实际游戏效果还需要结合功能文档和运行结果理解。

本节使用[资料指南](../misc/source_guide.md)记录的BDS稳定版快照。旧版`.mcschema`与标准JSON Schema是不同的表示方法，应当分别阅读。

## 从一个真实组件开始

我们查看该快照中的[`minecraft_durability.json`](https://github.com/bedrock-apis/bds-docs/blob/5c1713697a9fcf0e7491574303a742432e5ee8e2/metadata/json_schemas/server/item/1.20.50/minecraft_durability.json)。这个文件的`title`为`minecraft:durability`，顶层`type`为`object`，`properties`中包含`max_durability`和`damage_chance`，`required`数组中则包含`max_durability`。

这里有两类容易混淆的文件：我们正在阅读的文件描述组件的格式；我们真正编写的物品文件则使用这个组件。我们不会将`properties`和`required`原样放入物品的组件定义。

根据这份模式，我们可以写出如下组件片段：

```json
{
    "minecraft:durability": {
        "max_durability": 100,
        "damage_chance": {
            "min": 100,
            "max": 100
        }
    }
}
```

这是要放入物品`components`中的片段，并非独立的完整物品文件。完整物品的外层结构见[自定义物品](../primer/sec4.2.md)。我们将耐久上限设为100，是为了让后续测试易于观察；这份片段本身并不定义所有会消耗耐久的使用方式。

## 类型、必要字段与默认值

模式中`max_durability`的类型是`integer`，并且给出了`minimum: 0`。所以字符串`"100"`与整数`100`不是等价的输入，小数也不满足此处的整数要求。`required`意味着这个字段需要出现在相应对象中，不能因为我们觉得有一个“通常的默认值”就将它省略。

`damage_chance`的结构通过`$ref`引用另一个文件，并带有默认范围。我们看到引用时，需要相对于当前模式文件的位置找到被引用文件；不能将`$ref`当作作者给组件填写的字段。某个编辑器能够读取本页，却找不到引用目标时，其校验结果可能是不完整的。

这里还出现了`x-underlying-type`、`x-ordinal-index`和`x-runtime-constraint-description`等扩展信息。它们可以帮助理解导出系统和运行时限制，但不能直接当作物品组件中的新字段。尤其是运行时约束的文字说明，不一定会被通用JSON Schema校验器执行。

因此，一个合理的检查顺序是：先确认JSON语法，再解析模式及其引用，最后在目标游戏中测试组件效果。每一步解决的问题不同，我们不能用其中的一步替代其余步骤。

## 模式目录的版本不等于导出程序的版本

本次读取的文件位于`1.20.50`目录，而整个BDS快照报告的是更高的构建版本。这并不矛盾：目录可以表示某一格式从哪个版本开始使用，而快照版本表示我们从哪个构建获得了这份记录。

我们整理资料时，至少应同时保存“产物来自什么游戏构建”和“该模式描述什么格式版本”。如果只留下后一个数字，几年以后再次阅读时，便无法判断这份文件是旧程序当年的产物，还是新程序仍然保留的兼容模式。

## 如何阅读旧版`.mcschema`

旧模式文本中可能出现`string`、`object`、`array`、`opt`和带名称的子模式。它们用于表达结构，不是可以直接导入游戏的JSON。例如，`opt`通常用来标记可选内容，而类似`<any array element>`的文本描述的是元素位置，并不是要求开发者填写的键名。

遇到这种文本时，我们可以先列出字段名称，再标注类型、可选性和引用目标，最后建立实际JSON示例。暂时无法判断的语法应保留原文及出处，不要擅自将其转换为看似精确的运行结论。

更重要的是，旧导出器可能只遍历了能够到达的注册项。一个组件没有出现在导出目录中，可能意味着它已经改用另一套解析器，也可能意味着该宿主没有包含它。**没有导出文件，不能单独证明游戏完全不支持该功能。**反过来，存在导出文件也不能证明它对新的第三方包公开可用。

## 为一条结论留下证据

假设我们准备在教程中写下“这个字段必须为整数”。我们至少应记录对应模式的路径、快照提交，以及`type`所在的对象。如果进一步写下“这个配置会在玩家攻击时消耗耐久”，便还需要记录使用条件、相关组件和游戏内测试结果。

完成阅读后，我们可以尝试一个小练习：只改变`max_durability`的类型，将整数改为字符串，观察编辑器或校验器的报错。然后恢复正确类型，再在测试包中检查实际使用效果。这样，我们便把“能够读懂模式”推进到了“能够说明模式检查到了什么”。
