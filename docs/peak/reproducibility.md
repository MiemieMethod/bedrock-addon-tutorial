# 组织可以复现的作品

当我们能够制作一个功能之后，接下来的目标便是让另一个开发者也能在相同条件下得到相同结果。一份包含许多文件的压缩包，未必已经达到了这个目标：读者仍然可能不知道应该加载哪个世界、打开哪些实验功能，以及从哪里开始操作。

本节将把前面各章中的开发、测试和资料阅读方法组合起来，整理一份能够交接、比较和继续维护的作品。

## 将作品与测试条件放在一起

首先，我们在作品说明中写出一个可以独立完成的目标。例如：“玩家进入指定区域后收到一次提示，离开并重新进入时不重复提示。”这个目标比“实现遗迹系统”更适合验证，因为读者可以直接判断结果是否符合描述。

然后，我们列出资源包、行为包以及可选测试世界之间的关系。每个包的清单负责描述自身，而说明文档负责告诉读者如何使用这些包。需要相互配合的内容应当一起交付，不能仅提供行为文件却省略必要的客户端资源。

对于运行环境，我们记录完整游戏构建、客户端或BDS、脚本模块依赖和实验开关。不能只写“最新版”，因为这句话在另一个时间会指向另一个程序。

## 一个可直接填写的测试记录

我们可以在作品中增加如下说明，并将尖括号中的内容替换为实际值。这是测试记录的模板，不是可以直接作为清单加载的配置。

```text
作品：<名称与版本>
目标：<一次可以观察的功能>
游戏：<完整构建号>
宿主：<客户端 / BDS>
资源包：<包标识与版本；没有则写无>
行为包：<包标识与版本>
脚本依赖：<逐项记录模块及版本；没有则写无>
实验开关：<逐项列出；没有则写无>
世界：<新世界或测试存档，以及相关设置>
操作步骤：<从加载世界到触发功能的完整过程>
预期结果：<能够明确判断的现象>
实际结果：<通过 / 失败 / 未执行，并补充现象>
日志：<随包日志文件的位置或明确说明无日志>
```

其中，预期结果在测试之前填写，实际结果在测试之后填写。我们应当避免在模板中预先写下“测试通过”，否则记录很容易变成事后补写的结论，而不是帮助研究的过程。

## 为文件保留可以比较的身份

如果作品使用Git维护，可以通过提交固定一组文件。若只能通过压缩包交付，则可以同时记录文件的校验值。这样，当两个开发者得到不同结果时，便可以先确认他们使用的是不是同一份文件。

例如，在PowerShell中，可以针对已经生成的作品压缩包计算SHA-256：

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath .\TutorialAddon.zip
```

校验值用于比较文件内容，并不证明内容能够正常运行，也不表示它通过了安全检查。它解决的问题只是“我们手中的文件是否相同”。如果修改了压缩包，就需要重新生成对应校验值。

对于从游戏中导出的模式，也应该保留相似信息。导出器版本、游戏版本和产物文件共同决定了这次观察的上下文。只有导出器仓库地址而没有实际产物，无法复现对某个内部字段的判断。

## 为作品设计分层检查

我们可以将检查分为四层。第一层检查文件能否被读取，例如JSON语法和JavaScript语法。第二层检查包是否被游戏加载，包括清单、依赖和内容日志。第三层执行具体功能，比较预期现象。第四层检查保存、重进、多人和版本迁移等场景。

如果第一层失败，通常应先修复文件结构；如果只有第四层失败，则需要研究状态保存、事件重复触发或宿主差异。分层的意义是帮助我们缩小问题，而不是将所有检查都归为一句“运行失败”。

在自动化工具中，我们也应保留这样的边界。一个脚本能够遍历所有JSON并成功解析，是有用的结果；它还没有检查游戏是否认识每一个组件。站点能够构建完成，则说明文档具备可生成页面的结构；它还没有证明页面中的每条游戏命令都经过了实际运行。

## 将改动说明写给下一位维护者

完成修复后，我们记录原来的现象、修改的文件、修复后观察到的结果，以及尚未覆盖的条件。比如，“修正配方结果数量，在指定客户端中新建世界验证成功，尚未在BDS验证”，已经足以帮助下一位维护者决定从哪里继续。

如果我们改变了作品中的持久标识，还应说明旧存档是否需要迁移。仅为了让导入提示消失就重新生成所有标识，可能会使游戏将旧作品与新作品视为不同内容，所以包的标识变化应当是有目的的操作。

到这里，我们已经将一个“自己能够做出来”的功能，整理成了别人能够理解并继续验证的作品。接下来可以从[数据与脚本联动案例](../advanced/sec3.1.md)中选择一个功能，按照本节的格式补全自己的运行记录，再邀请另一位开发者按记录复现。
