# 版本、资料来源与验证范围

在阅读附加包教程时，我们经常会遇到这样一种情况：两个示例看起来都没有写错，其中一个可以被游戏读取，另一个却报出了未知字段。除了文件本身的语法之外，我们还需要检查一个容易被忽略的条件，那便是示例所针对的游戏版本。

本教程以国际基岩版的资源包、行为包与脚本系统为对象。中国版的模组SDK、编辑器扩展和独占组件具有各自的运行环境，不能仅因为文件都是JSON，便直接放入国际版使用。带有“历史”说明的页面用于理解旧作品；带有“预览”说明的内容需要根据指定版本单独检查。

## 区分我们正在谈论的版本

**游戏版本**决定了运行程序包含哪些功能。**格式版本**（**Format Version**）决定某个文件采用的格式及相应兼容行为。包在清单中的`version`则是开发者给自己的作品编写的版本。脚本依赖还具有独立的**模块版本**（**Module Version**）。这几类版本之间有关联，但它们并不是同一个数字。

例如，一个在较新游戏中运行的资源包，依旧可能使用`"format_version": 2`的清单和`"format_version": "1.10.0"`的客户端实体文件。我们不能为了让作品“升级”，便将所有`format_version`统一替换为游戏的版本号。正确的做法是分别查阅对应文件格式，确认所使用字段的要求，再修改必要的部分。

本教程的简单示例有意使用已知的格式或脚本模块基线；这些数字说明示例的要求，并不表示它们是当前最大的版本号。每章提供的格式前提、实验开关和宿主要求，应当和示例一起阅读。

## 各种资料分别能回答什么问题？

[官方稳定版文档](https://learn.microsoft.com/en-us/minecraft/creator/?view=minecraft-bedrock-stable)用于了解公开支持的接口、功能要求和推荐操作。[实验版文档](https://learn.microsoft.com/en-us/minecraft/creator/?view=minecraft-bedrock-experimental)还会包含尚处于预览阶段的内容。即便网页可以打开，也仍需查看具体成员的说明和实验要求，不能只根据地址中的视图名称判断稳定性。

Mojang示例库可以帮助我们观察实际文件的组织方式和原版内容之间的引用。原版文件有时还具有内部兼容路径，所以“原版正在使用”与“新的第三方包可以照搬”之间仍然需要验证。

BDS导出资料可以帮助我们核对字段类型、枚举、模块签名和部分运行时约束。导出内容中出现一个名称，说明该快照暴露了有关信息；它本身不保证任意平台、任意实验设置和任意包格式都能使用该内容。客户端和服务端的导出也应当分别记录。

当几种资料给出的描述不一致时，我们先记录冲突对应的版本与字段，再建立最小测试包。不要通过随意切换实验开关和格式版本，让多个变量同时变化，否则即便偶然获得了正确结果，也难以解释是哪一项改动发挥了作用。

## 关于旧版模式导出器

本次查阅的[LL Legacy Schema Exporter提交](https://github.com/LPaicen/ll-legacy-schema-exporter/tree/b307e48753e1944458d883705b0eb52fb901b9f3)在说明中明确绑定`1.26.20.04`客户端的二进制布局，输出目录为Mod数据目录下的`mcschema/1.26.20.04/`。其说明还指出，未注册的内容、已移除的内容和仅存在于服务端的模式不一定能够从客户端恢复；达到导出上限的文档可能不完整。

与之相比，本次查阅的[LeviLamina v26.51.7](https://github.com/LiteLDev/LeviLamina/releases/tag/v26.51.7)构建文件引用的是`v26.51.1`系列客户端与服务端运行时数据。因此，不能仅将旧导出器放入新的运行环境，就推定能够取得正确数据。

**本次撰写没有取得该导出器从最新受支持客户端和BDS生成的实际产物，也没有在这些宿主中执行导出。**教程不会将导出器源代码、README或旧版推测标为新的导出结果。后续如要用这些产物补充结论，应同时保留游戏构建号、客户端或服务端标记、LeviLamina版本、导出器提交、日志以及产物校验值。具体阅读方法见[阅读导出模式](../peak/schema.md)。

## 阅读与验证的边界

本教程中的“预期结果”用于说明读者完成操作后应观察什么，不等于编写时已经完成了游戏内测试。JSON解析、JavaScript语法检查和文档构建，分别只能验证各自的结构，不能代替客户端渲染、BDS加载或多人交互测试。

我们实际调试作品时，应将“文件语法通过”“游戏完成加载”“功能出现预期结果”和“保存重进后仍然正确”分开记录。这样，其他开发者才可以知道已经确认了哪些事实，以及还需要在哪些条件下继续测试。
